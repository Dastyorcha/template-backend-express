# Auth

## JWT

Tokens are generated by `src/utils/generatetoken.ts`:

- Payload: `{ userId: string }`
- Expiry: 72 hours
- Secret: `env.JWT_SECRET` (zod-validated at boot; minimum 16 characters)

The secret **must** be rotated when forking. Add to `.env` and rotate immediately in production.

## Auth middleware

`src/middlewares/auth.middleware.ts` runs on every private route:

1. Reads `Authorization: Bearer <token>` from the request header.
2. Verifies the JWT with `env.JWT_SECRET`.
3. Stores the decoded payload as `res.locals.user = { userId: string }`.
4. Calls `next()` on success, or responds 401 on missing/invalid token.

`res.locals.user.userId` is typed via `src/types/express.d.ts`. Never read `userId` from `req.body` or `req.query` for ownership checks — always use `res.locals.user.userId`.

## Registration flow (two-step email verification)

```
POST /api/users/register  { name, email, password }
  → validate fields
  → check email not already registered
  → generate 6-digit code
  → store { code, expiresAt: now+3min, userDto } in verificationCodes Map (keyed by email)
  → send verificationCodeEmail to user
  ← 200 "Verification code sent to your email."

POST /api/users/verify-email-for-register  { email, code }
  → look up email in verificationCodes Map
  → check expiry (400 if expired, deletes entry)
  → check code match (400 if wrong)
  → hash password with bcrypt (cost 10)
  → create User document (name, email, hashedPassword, loginedCount: 1)
  → delete map entry
  → generate JWT
  ← 201 { name, email, token, loginedCount }

POST /api/users/resend-code  { email }
  → must have a pending entry in verificationCodes Map
  → generate new code + new expiresAt
  → send verificationCodeEmail
  ← 200
```

**Limitation**: `verificationCodes` is an in-process `Map`. Restarting the server clears all pending registrations. For multi-instance deployments, replace the Map with a Redis key-value store or a MongoDB collection with a TTL index.

## Login

```
POST /api/users/login  { email, password }
  → find user by email
  → check isBlocked
  → bcrypt.compare(password, hashedPassword)
  → increment loginedCount
  → generate JWT
  ← 200 { name, email, token, createdAt }
```

## Forgot-password / reset flow (two-step)

```
POST /api/users/forgot-password  { email }
  → find user by email
  → (always 200 regardless — no email enumeration)
  → generate 6-digit code
  → store { code, expiresAt: now+10min, userId } in passwordResetCodes Map
  → send passwordResetEmail
  ← 200 "If an account exists, a reset code has been sent."

POST /api/users/reset-password  { email, code, newPassword }
  → look up email in passwordResetCodes Map
  → check expiry (400 if expired)
  → check code match (400 if wrong)
  → hash newPassword with bcrypt (cost 10)
  → update only hashedPassword field
  → delete map entry
  ← 200 "Password reset successfully."
```

`passwordResetCodes` has the same in-process limitation as `verificationCodes`.

## Change password (authenticated)

```
PUT /api/users/change-password?id=<userId>   { oldPassword, newPassword }
  requires: Authorization: Bearer <token>
  → sanitizeId(req) — 400 if invalid
  → find user by id
  → bcrypt.compare(oldPassword, hashedPassword)
  → hash newPassword with bcrypt (cost 10)
  → update hashedPassword
  ← 200
```
